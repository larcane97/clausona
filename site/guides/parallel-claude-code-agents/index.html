Run parallel Claude Code agents on different accounts and models

When one job splits into five, subagents are the usual answer. They run out of sight, you can't step into one of them, and all five spend the same account. This setup runs every agent as its own Claude Code session that you can watch and interrupt, and sends each one to the account or model you choose: your work account, a second subscription, or an API model such as DeepSeek.

Updated October 8, 2026

Short answer. Superset runs each agent in its own git worktree and tab. clausona gives each of those agents its own profile: an account or an API endpoint. The superset-fleet skill lets one Claude Code session plan the work, start a worker per task on the profile your rules pick, answer and watch them, check each result and clean up. Install the skill once and ask:

claude plugin marketplace add larcane97/clausona
claude plugin install clausona@clausona

Where subagents fall short

Subagents are built for quick side errands inside one session. For several real tasks at once, three things get in the way:

  • A subagent runs inside its parent session. You see what it returns, not what it is doing, so a wrong turn shows up only at the end.
  • You can't type into a single subagent to correct it or answer it. Stopping one usually means interrupting the session that runs all of them.
  • Every subagent runs on the account of the session that started it. Five at once use up that account's 5-hour window five times as fast, and none of them can run on another account or on a model from another provider.

In Superset, each worker is an ordinary Claude Code session in its own tab and worktree. You can read along, answer its questions, or stop it, without touching the others.

How the fleet works

You talk to one Claude Code session in Superset, the orchestrator. With the superset-fleet skill it:

  1. Picks a profile for each task from your request, your rules and every profile's current usage, and shows you the plan.
  2. Starts the workers, one Superset workspace per task, named after the task and the profile so the sidebar shows which account runs where.
  3. Watches them: it answers their questions, tells you when one waits at a permission prompt, and hands a task to another allowed profile if an account reaches its limit.
  4. Checks each result itself: the commits, the diff and the checks the brief named. It reports what it verified separately from what the worker only claimed.
  5. Retires finished workers, after asking you by default. A worker is retired only when its branch is pushed and its worktree is clean; the branch stays.

Route each agent to an account or a model

A terminal full of agents doesn't decide which account or model each one runs on. The orchestrator follows, in this order, what you say in the conversation, then ~/.clausona/superset-fleet.json, then its defaults.

{
  "workers": ["claude:work", "claude:side", "claude:deepseek"],
  "routing": [
    "claude:deepseek takes tests and doc fixes, never changes under src/",
    "anything touching the release process goes to claude:work"
  ],
  "maxUsage": 80,
  "retire": "ask"
}
  • workers lists the only profiles that may be workers.
  • routing holds your own rules, in plain words. The orchestrator applies them when it fills in the plan.
  • maxUsage skips a subscription profile once its 5-hour or weekly usage reaches that percentage. The default is 90.
  • retire is ask (the default) or auto.

Whatever your rules leave open, the defaults decide: the orchestrator's own profile never takes a worker, profiles with more headroom are preferred and workers are spread across them, wide mechanical work goes to API profiles, and an independent check of risky work runs on a third profile. You can also change the file by asking, for example "never use claude:personal for workers".

Add an API model such as DeepSeek

Any endpoint that speaks the Anthropic Messages format can be a profile. DeepSeek serves one at https://api.deepseek.com/anthropic:

clausona add claude:deepseek --api \
  --base-url https://api.deepseek.com/anthropic \
  --model deepseek-v4-pro

clausona asks for the key without echoing it and keeps it in the macOS Keychain or ~/.clausona/secrets.json. The profile shares your skills, hooks and plugins like any account. OpenRouter, a gateway, or a model you serve yourself work the same way.

  • Give API workers small, explicit briefs: the file, the function, the change and the command that checks it. Long exploratory briefs overflow smaller context windows.
  • Give their Superset agent a short tool list, such as --tools=Bash,Read,Edit,Write,Grep,Glob, to keep tool definitions out of the context.
  • Check whether the endpoint honors prompt caching. Without it, every turn re-reads the whole conversation and long sessions slow down.

Compared with subagents and herdr

herdr is a terminal runtime for coding agents: it keeps agent panes running in the background, marks each one working, blocked or idle, and lets agents open panes and prompt each other. It doesn't decide which account or model an agent uses; a pane runs whatever you start in it. clausona adds that, and the two work together: start a herdr pane with clausona run claude:work and it runs on that account.

Set it up

  1. Install clausona and add a profile per account or API endpoint.

    clausona add claude:work
clausona add claude:side

  2. In Superset, open Settings, then Agents, and add a custom agent per profile. Command: the output of command -v clausona. Arguments, for example:

    run claude:work -- --model claude-sonnet-5-5 --effort high --permission-mode acceptEdits --strict-mcp-config

    Put the model and effort here, because Superset doesn't pass them to custom agents. --strict-mcp-config keeps a worker from stopping at Claude Code's "new MCP servers found" question. Without the Superset CLI logged in, the skill can add these agents for you, after asking.

  3. Start each new profile once by hand, so its one-time questions are answered before a worker meets them.

    clausona run claude:deepseek

  4. Install the plugin. Plugins are shared across profiles, so one install reaches all of them.

    claude plugin marketplace add larcane97/clausona
claude plugin install clausona@clausona

Limits

  • Workers are Claude Code sessions. Codex workers aren't covered yet.
  • Superset has to run on the same machine, as the desktop app or superset start.
  • Without the Superset CLI logged in, the skill talks to the Superset app's local host service through a bundled helper. That service isn't a documented API; if an update changes it, the helper says so and stops.

Questions

Does the orchestrator run workers on its own account?

No. The profile the orchestrator runs on only coordinates; workers go to other profiles.

Can retiring a worker lose work?

A worker is retired only when its work was checked, its branch is pushed and its worktree is clean. The skill's helper checks the branch and the worktree again right before it deletes the workspace, and refuses when either isn't clean.

Do I need Superset to give agents different accounts?

No. clausona run claude:work starts a Claude Code session on that account in any terminal, tmux or herdr pane. Superset and the skill add a coordinator that plans the work, routes it, watches the workers and checks their results.

What happens when an account reaches its limit mid-task?

The orchestrator hands the task to another profile your rules allow, in the same workspace, and closes the stopped worker's terminal.
