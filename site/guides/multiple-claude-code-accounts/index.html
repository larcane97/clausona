How to use multiple Claude Code accounts on one machine

Logging out of a work account just to sign in to a personal one gets tiring fast. Give each account its own config directory and both stay signed in with the same setup. They can even pick up the same conversation.

Updated November 9, 2026

Point CLAUDE_CONFIG_DIR at a separate directory for every extra account. Then link everything except the sign-in and the account's own state back to your main ~/.claude.

clausona does that in three commands:

clausona init              # register the account already signed in
clausona add claude:work   # a second account, with Claude Code's own sign-in
csn use work               # plain `claude` now starts as that account

If you want to stay in the same conversation after switching accounts, run clausona config claude:work --merge-sessions once to share history. After that, claude --continue resumes the latest conversation in the folder no matter which account started it.

Why a second account is awkward

Claude Code keeps one signed-in account at a time.

Switching with /logout and /login works, but you have to sign in again. And one terminal can't stay on your work account while another uses your personal one.

The CLAUDE_CONFIG_DIR environment variable moves Claude Code's whole config directory, so a second directory can hold a second sign-in.

But the new directory starts empty. Your settings and hooks aren't there, and neither are your skills or plugins. CLAUDE.md and your history stay behind too.

Install a plugin under one account and the other doesn't have it. From there, the two setups drift apart.

Do it by hand with CLAUDE_CONFIG_DIR

Keep ~/.claude as your main directory. Give the second account a new one, and link into it whatever both accounts should share:

# a directory for the second account
mkdir -p ~/.claude-work

# link what both accounts should share
for item in settings.json CLAUDE.md skills commands agents hooks; do
  [ -e ~/.claude/$item ] && ln -sn ~/.claude/$item ~/.claude-work/$item
done

# start Claude Code there and sign in with the second account
CLAUDE_CONFIG_DIR=~/.claude-work claude

Hooks are configured in settings.json, so linking it shares them. It also shares your permissions, status line and model choice.

The hooks link covers scripts you keep in ~/.claude/hooks.

Then add an alias for the second account:

alias claude-work='CLAUDE_CONFIG_DIR=~/.claude-work claude'

On Windows, you can do the same thing in PowerShell. A junction links a folder without needing admin rights:

# a directory for the second account
New-Item -ItemType Directory -Force "$HOME\.claude-work" | Out-Null

# link the folders both accounts should share
foreach ($item in 'skills', 'commands', 'agents', 'hooks') {
  if (Test-Path "$HOME\.claude\$item") {
    New-Item -ItemType Junction -Path "$HOME\.claude-work\$item" -Target "$HOME\.claude\$item" | Out-Null
  }
}

# a command for the second account; sign in on its first run
function claude-work {
  $env:CLAUDE_CONFIG_DIR = "$HOME\.claude-work"
  try { claude @args } finally { Remove-Item Env:CLAUDE_CONFIG_DIR }
}

Individual files like settings.json and CLAUDE.md need symbolic links, and Windows only lets you create those with Developer Mode turned on. Hard links won't work because Claude Code saves those files by replacing them.

Leave CLAUDE_CONFIG_DIR unset for your main account. Claude Code treats any value as a separate directory, even ~/.claude. With the variable set, it reads ~/.claude/.claude.json instead of ~/.claude.json. On macOS it also looks for a different Keychain item. You land in a second identity that isn't signed in. (Checked with Claude Code 2.1.278 on macOS.)

What must not be shared

A few things must stay out of the links.

  • .claude.json records which account is signed in. It also holds the MCP servers added with claude mcp add. Link it, and the directories lose track of which account they belong to. To use an MCP server under both accounts, add it to both or put it in a project's .mcp.json.
  • .credentials.json holds the sign-in tokens on Linux and Windows. On macOS it's used only when the Keychain refuses them. Otherwise the tokens sit in the Keychain under a name derived from the config directory, so two directories never share them.
  • plugins/ as a whole. Two files in it store absolute paths into the config directory: known_marketplaces.json and installed_plugins.json. Link the rest of plugins/. Keep a copy of those two files per directory, with the paths pointing at that directory. Update the copies whenever you add or remove a plugin.
  • Small per-directory state, such as .last-update-result.json. Claude Code rewrites it as a new file, and it describes one directory only.
  • State Claude Code keeps for the signed-in account, such as policy-limits.json and remote-settings.json, your org's policy limits and managed settings. mcp-needs-auth-cache.json, state/ and the background daemon's daemon/ are among them too. Link one, and the second account reads the first account's copy. With the policy limits, it can apply the other org's until Claude Code fetches its own. (Checked with Claude Code 2.1.299.)

Newer Claude Code versions also add directories.

A link you made today doesn't cover a directory that appears next month. The second account quietly ends up with a separate copy, so check your links after you update Claude Code.

This upkeep is where the manual setup wears thin.

Let clausona do it

clausona is a free, open-source account switcher for Claude Code and Codex CLI. It handles the setup above for you and keeps it intact. Install it:

macOS and Linux curl -fsSL https://github.com/larcane97/clausona/releases/latest/download/install.sh | bash
Windows PowerShell irm https://github.com/larcane97/clausona/releases/latest/download/install.ps1 | iex

Then register the account you're signed in to, and add the others:

clausona init              # registers the accounts already signed in
clausona add claude:work   # makes ~/.claude-work and opens Claude Code's sign-in
csn use work               # plain `claude` now starts as the work account
csn use claude:default     # back to the first account; init names it default

clausona gives each account a directory. It links everything from ~/.claude into it except the sign-in, the account file, per-directory state and what Claude Code keeps for one account, like the org's policy limits. Conversation history stays out too, unless you merge sessions.

So settings, hooks, skills, commands, agents, plugins and CLAUDE.md are the same under all of them. clausona also keeps the two plugin files in step, account by account.

When a newer Claude Code adds a directory, clausona doctor reports that it isn't linked yet. clausona repair <profile> links it.

csn is the short name for clausona.

There's no wrapper around Claude Code. A shell hook sets CLAUDE_CONFIG_DIR for the run and starts the real claude, and nothing stays running in the background.

A plain claude launch reads a cached script in the shell, so Claude Code starts as fast as it does without clausona. clausona's own process runs on the first launch after you change something, such as csn use, and on every launch of an API profile. clausona run starts it every time, routed or not.

Share conversation history between accounts

Conversation history lives in projects/. Two directories next to it refer to it by session id: jobs/ for background sessions, and teams/.

Share all three or none of them. A background session can't be resumed if its record and transcript sit in different directories.

With clausona, it's one switch per account:

clausona config claude:work --merge-sessions

Turning it on first copies the account's existing conversations into the shared history, so none are lost.

From then on, claude --resume lists conversations from all the accounts that share history.

claude --continue picks up the latest one in the current folder, whichever account started it. A /goal set in that conversation comes back with it.

--separate-sessions turns it off.

You can also pass --merge-sessions to clausona add or clausona init.

Use two accounts at the same time

csn use sets the account that new claude launches use. To run one session under another account without changing that, start it with clausona run:

clausona run claude:work

One terminal can stay on your main account while another runs the work one, on the same setup.

Arguments after -- go to Claude Code.

See how much each account has left

clausona list shows each account's weekly limit, plus the 5-hour limit on plans that have one. It queries Claude Code's usage endpoint using the credential Claude Code saved for that account:

PROFILE             ACCOUNT              5H         7D
claude:work         dev@example.com      62% 1h     41% 3d
claude:personal     me@example.org       8%         77% 5d
claude:team         team@example.com     none       30% 4d

Verified Ultra plans don't have a 5-hour limit, so the 5H column shows none, like claude:team here.

Running csn with no arguments opens a dashboard with the same readings and the exact reset times.

Optimize usage across multiple accounts with dynamic routing

With two accounts, it's easy to burn through one while the other sits unused.

With dynamic routing, clausona picks an account for you whenever a run starts. It checks current usage across your accounts and starts on one with room. Because accounts take turns, usage stays spread out instead of piling onto a single account.

You set it up as a route, a named group of your accounts:

clausona route add main        # every Claude Code account, taking turns
clausona route explain main    # who a run would get now, and why
clausona run --route main      # Claude Code starts on that account

If an account reaches 80% or more of its weekly limit, or its 5-hour limit when it has one, it sits out while another account is still under 80%. Each run prints one line naming the account it picked.

A route doesn't need every account. clausona route add work --from '*@work.example' takes only the accounts on your work email. After clausona route dir ~/work work, a plain clausona run claude anywhere under ~/work starts on one of them.

Plain claude isn't routed. It still starts on the account csn use set.

If every account in the route is used up, nothing starts, and clausona says when each one resets. The routing docs cover the rest, including waiting for an account to free up.

The pick happens once, when the run starts. A running session never moves to another account.

Keep the accounts to what they're for, such as work and personal use, within Anthropic's terms.

Questions

How do I check which account Claude Code is using?

Run /status inside a Claude Code session to see which account is signed in. From your terminal, csn current prints the profile that a plain claude command starts with, and clausona list marks that profile with ▸.

Can I just switch with /logout and /login?

Yes, if you only use one account at a time. You have to sign in through the browser on every switch, and new sessions in any terminal will start as whichever account logged in last. Giving each account its own directory keeps both signed in so any terminal can stay on either one.

Can I continue a conversation under another account?

Yes, once your accounts share history. Run clausona config claude:work --merge-sessions for each account that should share sessions. After that, claude --continue picks up the latest conversation in the folder no matter which account started it, and claude --resume lists all of them.

Does each account keep its own usage limits?

Yes. Usage limits belong to each account, and clausona does not change them. You can run clausona list to see each account's weekly limit, along with its 5-hour limit on plans that have one.

Is it OK to use more than one account?

clausona doesn't change what any account is allowed to do. It only keeps each sign-in in its own directory. Use each account for what it's meant for, such as work and personal projects, within Anthropic's terms.

How is clausona different from other account switchers?

Tools like claude-swap and ClaudeCodeMultiAccounts swap one sign-in inside ~/.claude by default, leaving one account active at a time. clausona gives each account its own config directory and links your setup into it. Two accounts can run at once, and history is shared only when you turn it on. It works the same way for Codex CLI. The comparison covers claude-swap, ccam, aisw, codex-auth and more.

Can I be signed in to two Claude Code accounts at once?

Yes, with one config directory per account. Two terminals with different CLAUDE_CONFIG_DIR values run two accounts side by side. clausona run claude:work starts one session under another account without changing the default.

Do MCP servers carry over to the other account?

Servers that come with a plugin do, because plugins are shared. Servers added with claude mcp add don't. They're stored in that account's own .claude.json, and that file must not be shared. Add them under the other account too, or put them in a project's .mcp.json. The Extensions guide shows which account has which.

Does clausona switch accounts automatically when I hit a limit?

A running session never moves to another account. With a route, clausona picks the account when a run starts. clausona run --route main gets one that still has quota left. Set a directory rule or a default route, and plain clausona run claude does the same. clausona use and clausona run <profile> leave the choice to you. Keep the accounts to what they're for, such as work and personal use, within Anthropic's terms.

Does clausona slow down Claude Code's start?

Not a plain claude launch. That reads a cached script in the shell. On an M4 Pro Mac, claude --version took a median 25 ms with the hook and 25 ms without it. clausona run starts clausona's own process first, routed or not, and that takes about a third of a second. The first launch after a change such as csn use starts it too, and so does every launch of an API profile.

Is my sign-in ever shared?

No, credentials and .claude.json stay with their account.

Does it work with tools that start Claude Code themselves?

The shell hook covers claude started from your shell. A tool that launches Claude Code itself, such as Paradev (formerly Superset), can start clausona run claude:work -- <args> instead, and it then runs on that account. Give it clausona's full path, which command -v clausona prints.

Can a profile use an API key or another model?

Yes. clausona add claude:gw --api --base-url <url> adds a profile for the Anthropic API, a gateway such as OpenRouter, or a model you serve yourself. It shares the same setup and switches like any account.

Does it work on Windows?

Yes, in PowerShell 5.1 or later. Shared directories are junctions. Turn on Developer Mode. Without it, settings.json, CLAUDE.md and keybindings.json stay a per-account copy, because Claude Code replaces them on every save. clausona doctor says so.
