clausona / 에이전트 병렬 실행

tmux에서 Claude Code와 Codex 에이전트를 계정별로 병렬 실행하기

에이전트를 tmux 창 하나에 하나씩 띄워 쓰는 분이 많습니다. 여기에 clausona를 더하면 창마다 다른 계정으로 Claude Code(클로드 코드)나 Codex를 돌릴 수 있어요. DeepSeek 같은 API 모델도 됩니다.

2026년 10월 16일 업데이트

tmux-fleet 플러그인을 설치합니다. 조율 플러그인들이 함께 쓰는 규칙인 fleet-core도 같이 설치됩니다.

claude plugin marketplace add larcane97/clausona
claude plugin install tmux-fleet@clausona

그다음 tmux pane에서 Claude Code를 띄우고 이렇게 요청합니다. "이 작업들을 tmux에서 내 계정들에 나눠 줘: CONTRIBUTING.md는 DeepSeek(claude:ds-flash)로 쓰고, .editorconfig는 Codex(codex:personal)로 추가해 줘."

그러면 계획을 세우고 작업마다 tmux 창을 하나씩 엽니다. 각 워커는 정해진 계정으로 돌아가요. 정리하기 전에는 워커가 낸 결과를 직접 확인합니다.

tmux에서 보이는 것

워커마다 git worktree가 따로 만들어지고, 지금 쓰는 tmux 세션에 창(window)이 하나씩 생깁니다. 창 이름은 docs · ds-flash처럼 작업과 clausona 프로필로 붙습니다. 그래서 상태 표시줄만 봐도 어느 계정이 무엇을 하는지 보여요.

prefix 키와 창 번호를 누르면 그 워커로 옮겨 갑니다. 지켜보다가 직접 입력해도 됩니다. 하나가 엉뚱한 쪽으로 가면 그것만 멈추고, 나머지는 그대로 두면 됩니다.

다만 tmux는 에이전트가 아직 일하는 중인지 스스로 알지 못합니다. 그래서 워커가 직접 알립니다.

Claude Code 워커는 그 워커만 쓰는 hook을 받습니다. worktree 안의 .fleet-claude.json을 --settings로 넘기는 방식이라, 공유하는 settings.json은 건드리지 않아요.

Codex 워커에게는 승인을 기다리거나 턴을 마치면 터미널 벨을 울리라고 지시합니다. 그 창에 걸린 tmux hook이 벨을 기록하고, 상태 표시줄의 그 창에는 !가 붙습니다.

두 신호 모두 worktree의 .fleet-events.jsonl에 이벤트로 쌓입니다. 메인 세션은 플러그인에 함께 들어 있는 작은 Node 스크립트로 이 이벤트를 기다립니다.

실행 흐름

메인 세션은 먼저 clausona list로 프로필을 읽고 작업마다 하나씩 고릅니다. 요청에도 fleet.json에도 계정이 정해져 있지 않으면, 계획을 보여 주고 확인을 기다립니다.

그다음 작업마다 ~/.clausona/worktrees/<repo>/<task>에 fleet/<task> 브랜치로 worktree를 만듭니다. 같은 tmux 세션에 창을 열고, 그 창의 셸에 고른 프로필로 clausona run을 입력합니다.

브리프는 worktree 안의 .fleet-*.md 파일에 넣습니다. 워커에게는 그 파일을 읽으라는 한 줄만 보내요. .fleet-* 파일은 모두 저장소의 .git/info/exclude에 올라가서 커밋에 섞이지 않습니다.

신호는 놓칠 수도 있습니다. 일하던 워커가 3분 동안 아무것도 출력하지 않고 이벤트도 없으면, 기다리던 메인 세션이 그래도 깨어납니다. 신호 하나 놓쳤다고 실행 전체가 멈춰 서지는 않아요.

워커가 끝났다고 하면 메인 세션이 직접 확인합니다. 커밋과 diff를 보고, 브랜치가 깨끗한 상태로 push됐는지도 봅니다.

확인이 끝나면 git worktree remove로 worktree를 지웁니다. 기본값은 사용자가 승인한 뒤에 지우는 것이고, retire가 auto면 바로 지웁니다. --force는 붙이지 않아서, 변경이 남은 worktree는 git이 지우지 않습니다. 그럴 때는 워커를 그대로 둡니다. 지우고 나면 창이 닫히고, 브랜치는 남아요.

어떤 프로필이 이 저장소를 처음 열면 Claude Code나 Codex가 폴더를 신뢰할지 묻습니다. 메인 세션은 워커 화면을 읽고 키를 보내 답하는데, 작업을 맡긴 저장소일 때만 답합니다.

워커가 사용량 한도에 걸려 멈추면, 메인 세션은 그 워커의 창에 다른 프로필로 새 pane을 열어 작업을 넘깁니다. 원래 pane은 닫습니다.

Codex를 메인 세션으로 쓰기

Codex도 조율을 맡을 수 있습니다. Codex에 플러그인을 설치하면 되는데, Codex는 플러그인 의존성을 지원하지 않아서 fleet-core를 따로 추가해야 합니다.

codex plugin marketplace add larcane97/clausona
codex plugin add fleet-core@clausona
codex plugin add tmux-fleet@clausona

Codex 메인 세션은 워커를 몇 분씩 끊어서 기다립니다. Codex에는 세션을 깨워 줄 백그라운드 작업이 없거든요.

Codex로 조율하면 워커도 기본으로 Codex 계정을 씁니다. Claude Code로 조율하면 Claude Code 계정을 쓰고요. 다른 도구의 프로필은 직접 지정하거나 workers에 넣어 둔 경우에만 워커가 됩니다.

Codex 워커는 --disable hooks로 띄웁니다. 그래야 Codex의 "Hooks need review" 화면에서 멈추지 않아요. hook을 신뢰할지는 여전히 사용자가 정합니다.

Codex 기본 샌드박스에서는 Codex 워커가 .git에 쓸 수 없고 네트워크에도 나가지 못합니다. 그래서 커밋 전에 한 번, push 전에 또 한 번 승인을 묻습니다. 그 워커의 창에서 승인하면 됩니다.

알아서 하게 하려면 아래 설정 파일의 permissions에 "codexSandbox": "danger-full-access"를 넣으세요. 이러면 워커의 Codex 샌드박스가 꺼집니다.

Codex 설정에서 하나 더 볼 게 있습니다. [shell_environment_policy]에 inherit = "core"가 있으면, Codex가 실행하는 명령에서 TMUX가 보이지 않습니다. 그러면 메인 세션이 tmux 세션을 찾지 못합니다. 메인 세션을 -c shell_environment_policy.inherit=all로 띄우세요.

tmux에 bell-action none이나 current가 설정돼 있으면, 뒤에 있는 창의 Codex 워커 벨이 hook까지 닿지 않습니다. 이때 메인 세션은 3분 동안 조용한지 보는 확인으로만 그 워커를 알아챕니다.

설정

조율 플러그인들은 ~/.clausona/fleet.json 파일 하나를 함께 씁니다. 워커로 쓸 프로필 목록, 자연어로 적은 배정 규칙, 사용량 한도, 끝난 워커를 자동으로 정리할지를 여기에 적습니다. 각 키의 설명은 에이전트 병렬 실행 가이드에 있습니다.

말로 해도 됩니다. "claude:personal은 워커로 쓰지 마"라고 하면 메인 세션이 파일을 고쳐요.

자주 묻는 질문

메인 세션이 tmux 안에서 돌아야 하나요?

네. 플러그인은 $TMUX로 지금 쓰는 tmux 세션을 찾습니다. 그래서 Claude Code나 Codex를 tmux pane에서 띄우고, 거기서 요청해야 해요. tmux는 3.2 이상이어야 합니다.

SSH로 접속한 서버에서도 되나요?

됩니다. GUI 없이 에이전트가 돌아갈 컴퓨터에 tmux만 있으면 되거든요. 서버에 SSH로 들어가 tmux pane에서 Claude Code나 Codex를 띄우면, 워커도 그 세션의 창으로 열립니다.

Windows에서도 되나요?

WSL 안에서는 됩니다. tmux가 Windows에서 바로 돌아가지 않기 때문입니다. WSL 밖에서 쓰려면 Windows에서도 돌아가는 herdr나 Orca를 쓰고, herdr-fleet나 orca-fleet 플러그인을 설치하면 됩니다.

herdr나 Superset이 있어야 하나요?

아니요. Claude Code나 Codex 말고는 tmux와 clausona만 있으면 됩니다. herdr, Orca, Superset을 이미 쓰고 있다면 각각에 맞는 조율 플러그인이 따로 있고, 규칙은 같아요.

워커가 사용량 한도에 걸리면 어떻게 되나요?

메인 세션이 그 워커의 창에 새 pane을 열고, 규칙이 허용하는 다른 프로필로 작업을 넘깁니다. 멈춘 pane은 그다음에 닫습니다.

워커를 정리하다 작업이 날아갈 수 있나요?

커밋하지 않은 변경만 그럴 수 있습니다. 플러그인은 --force 없이 git worktree remove로 지우고, git은 그런 worktree를 지우지 않습니다. 지우기 전에 브랜치가 push됐는지도 확인해요. 둘 중 하나라도 걸리면 워커는 그대로 남습니다.

브리프 파일이 커밋에 섞이지 않나요?

섞이지 않습니다. 브리프와 후속 지시, hook 설정, 이벤트 기록이 모두 .fleet-로 시작하고, 이 패턴이 저장소의 .git/info/exclude에 들어갑니다. .gitignore는 건드리지 않습니다.
